# Migration + generated-ownership convention (WP-7 + WP-9)

## The two-doc front-door

Once a repo *adopts* generated comprehension docs, the front-door is split:

| Doc | Owner | Content |
|---|---|---|
| `PROJECT.md` (generated) | **code-comprehension** (regenerated) | Components table, structural Interaction Edges, external deps, entry points, testing — the *structural* facts that drift. |
| `ARCHITECTURE.md` (root sibling) | **human** | The *why*, integration-semantics judgment, external-service failure-impact prose, cross-repo notes — the things a generator **cannot** produce and must never fake. |
| `history.md` | **human / project-documentation** | Changelog / dated entries (a generator must NOT dump changelog into ARCHITECTURE.md — the S025 skill_factory finding). |

`CLAUDE.md`'s "read PROJECT.md first" survives and strengthens via a header pointer to `ARCHITECTURE.md` (the generated PROJECT.md carries `see_also: ARCHITECTURE.md`).

## `--migrate` is de-automated + human-gated (§12 C7+C11)

v1 `--migrate` does **NOT** auto-classify prose (semantic classification of changelog vs rationale vs structure is not mechanical). Instead `migrate.py`:

1. **C11 hard gate** — REFUSES to migrate if any component is `failed`/`gap`, source coverage is incomplete, or extraction ran below the LLM tier (degraded). Partial extraction must never silently become the authoritative doc.
2. **Archives** the original `PROJECT.md` + every `COMPONENT.md` byte-for-byte under `.comprehension/migration/<run>/` (rollback = the archive).
3. **Generates to the shadow path** (`.comprehension/PROJECT.generated.md`) — never overwrites the real doc until approved.
4. **Produces a migration manifest + diff + a *proposed* section-split** (suggestion only; keyword-bucketed, not semantic).
5. **Requires section-level human approval** (`--apply --approvals <file>`) before any relocation/overwrite. Idempotent; rollback = the archive.

**The v1 dogfood is shadow-only and NEVER calls `--migrate`** (§13), so no human pause is hit during the autonomous run. Adoption of any generated PROJECT.md remains a deliberate, separately-invoked, human-gated step.

## Generated-ownership banner + guard (WP-9 — SHIPPED in v1)

Every generated doc carries:

```
<!-- GENERATED by code-comprehension — do not hand-edit; edits are erased on regen; narrative → ARCHITECTURE.md -->
<!-- FRESHNESS:v1 generated_from=<16-hex content digest> -->
```

`ownership_guard.py` provides:
- `is_generated(path)` — banner detection.
- `freshness_ok(path, expected_digest)` — confirms the FRESHNESS stamp matches the recomputed `generated_from` digest.
- `lint_no_manual_edit(path, expected_digest)` — a freshness/pre-commit lint that FAILS (exit 2) on a generated doc whose stamp no longer matches its inputs (stale or hand-edited).

## Writer-contract migration (WP-9 — DEFERRED, adoption prerequisite)

Before ANY repo *adopts* a generated `PROJECT.md`, the writer contracts must be amended to detect the banner and **refuse to hand-edit**, redirecting human updates to `ARCHITECTURE.md` / `history.md`:

- `exit-with-docs` — must skip a banner-bearing `PROJECT.md`/`COMPONENT.md`.
- `project-documentation` — must not hand-update a generated doc; route changes to the sidecar.
- `forge` / `agent-teams` — must not write into a generated doc.

This contract migration is **DEFERRED** — it is an *adoption* prerequisite, NOT part of the v1 build/dogfood (the dogfood is shadow-only and never adopts). v1 ships the banner + the guard primitives (`ownership_guard.py`); the contract amendments land before first adoption. This honest scoping is per §12 C6 + §13.
