## Overview

A standing library of outside tools (apps, CLIs, models, services, libraries) foundry has looked at, used or not. One file per tool in `entries/`, a generated table in `INDEX.md`, and `scripts/radar.py` (stdlib only, any OS) to index, lint, search and list stale entries.

## When to use

- A question names a tool or a need: "any open voice-cloning tools?", "what did we decide about OpenCode?", "is there an Ahrefs alternative?"
- Someone shares a tool, video or repo: is it worth having?
- Before proposing a dependency or a skill for a capability: was a tool already assessed or held?
- A freshness pass (`stale`).

Not for: installing or running tools (owner's call); scoring a model (`model-eval-pack`); deep topic research (`web-research`, then file the result here); taking outside code in (`intake-scan`).

## Look up

Run from the skill directory (or put `--root DIR` before the command):

```bash
python3 scripts/radar.py find voice                  # name, slug, category, alternative_to, tags
python3 scripts/radar.py find seo --ring assess      # filter by ring
python3 scripts/radar.py find "" --category coding-agent
python3 scripts/radar.py stale                       # past review_by
python3 scripts/radar.py stale --days 30             # also falling due within 30 days
```

Or read `INDEX.md`. `find` exits 1 on no match (not assessed, not "none exists"); `stale` exits 1 when anything is due. Answer with the entry's ring and `reviewed` date, and flag it if past `review_by`.

## Rings (what each means for foundry)

| Ring | Meaning | Needs |
|---|---|---|
| adopt | In use, or approved by the owner for use | an `Approved by ...` line (owner, date); lint-enforced |
| trial | Worth trying on one real task now | the task, and a `Success: ...` line saying what the trial must show; lint-enforced |
| assess | Worth knowing; no use yet | the trigger that would move it to trial |
| hold | Do not use | a `Hold because ...` or `Reason: ...` line; lint-enforced |

A ring change is a dated decision in "Decision and next step"; anything that costs money or installs is the owner's call.

## Add a tool (intake)

**Ambiguity gate.** If the tool is not named precisely (namesakes, no URL, a video naming several), ask ONE compact question for the exact tool and URL first. If the requester cannot be asked, take the best-known namesake, list the rest under `## Other candidates`, and mark the identity UNCERTAIN until confirmed. An existing slug is updated, never duplicated.

1. **Primary sources first:** the project's repo, docs, licence file, releases, model card, pricing page. Videos, posts and marketing are claims to check. Tag every fact: VERIFIED (stated in a primary source, or observed in a read-only local check), LIKELY (implied by a primary source, or agreed by independent secondary sources), UNCERTAIN (unchecked, conflicting, or secondary-only on a point that matters). VERIFIED and LIKELY bullets carry `Source:` with URL and read date. Vendor-documented is not demonstrated: say "the docs say" when nobody has run it.
2. **Check the four things that decide fit:** licence (code separately from weights, models and data), maturity (latest release and its date, alpha or stable), cost (who pays for what, including data or API usage behind a "free" app), and MCP (server, client, both, none).
3. **Check the local environment read-only:** already installed, configured or served? Read config; change nothing.
4. **Map to foundry by search** of the skills tree: skills touched, gap filled, and conflicts with harness rules (roster and seats, agy family rule, provider diversity, skills-consumer vs delegate in `install.py`).
5. **Pick a ring with a reason**, write the verdict as one line, and set `review_by` (at most `reviewed` + 90 days, lint-enforced; shorter for alpha tools or fast-moving pricing).
6. **Install nothing, run nothing, sign up for nothing** without the owner's say-so. Spending decisions belong to the owner.
7. Copy the part of [the entry template](references/entry-template.md) below its rule to `entries/<slug>.md`, fill it, then run `python3 scripts/radar.py index` and `python3 scripts/radar.py lint` (must exit 0).

## Entry schema

Each entry opens with a fenced ```` ```radar ```` block of `key: value` lines (lists `[a, b]`, `#` comments), parsed without a YAML library.

| Field | Rule |
|---|---|
| name, slug | slug lowercase-hyphenated and equal to the file name |
| category | coding-agent, llm-model, llm-serving, seo-data, voice-audio, image-editing, image-generation, video, automation, observability, data, security, dev-tool, dev-methodology, git-tooling, other (extend in `scripts/radar.py` CATEGORIES) |
| alternative_to | what it replaces or competes with |
| homepage, repo | URL or `n/a` |
| licence_code, licence_other | code licence; weights/data/engine licence or `n/a` |
| cost | who pays for what |
| maturity | latest release and date (lint warns without a date) |
| mcp | server, client, both, none, unknown; `none` only when absence is established, else `unknown` |
| ring | adopt, trial, assess, hold |
| reviewed, review_by | YYYY-MM-DD; reviewed not in the future; the review date falls 1 to 90 days after reviewed |
| suggested_by | who asked (a role, not personal data) |
| related_skills, tags | lists; related skills should exist (lint warns) |
| verdict | one line, shown in INDEX.md |
| origin | optional: task id and review doc |

Body sections, all required by the lint: `## What it is`, `## Verified facts` (every bullet tagged; VERIFIED/LIKELY bullets carry `Source:`), `## Claims that are false or overstated`, `## Foundry fit`, `## Decision and next step`, `## Sources` (at least one URL outside code and comments). Optional: `## Other candidates` for namesakes. No section may be empty or repeated. Host-specific detail (addresses, auth posture, local config) stays in the review doc, not the entry.

## Freshness

An entry past its `review_by` is stale: its prices, licences and releases are history. Re-check by the intake method, update both dates, rerun `index` and `lint`. `INDEX.md` and the entry list above are generated: never edit them by hand; `lint` fails when they drift.

## Anti-patterns

| Don't | Why |
|---|---|
| Copy the video's or vendor's claims as facts | Marketing overstates; #369 found three of five headline claims overstated |
| One licence for a model or multi-engine app | Code, weights and data licences differ |
| Call a tool "free" because the code is | The data or API behind it may be paid (OpenSEO) |
| Install, sign up or run to "check quickly" | Needs the owner's say-so; read-only checks only |
| Make a tool a seat or delegate because it is good | Seats come from the roster and provider-diversity rules, not from the radar |
| Quote a stale entry as current | Run `stale`; re-check before relying on prices or releases |
| Put customer or business data in an entry | The library is general; a role in `suggested_by` is enough |
| A second entry for a renamed tool | Update the slug's entry and note the rename |
